# 비교 주장(Claim)별 Before-After Baseline 프로토콜

## 1. 목적: "개선했다"는 주장에 대한 입증 책임
- 에이전트가 코드를 수정하고 "버그를 고쳤다"거나 "성능이 향상되었다"고 주장할 때, 사전 측정치(Before Baseline)가 없으면 그 주장의 진위를 검증할 수 없습니다.
- Before Baseline 프로토콜은 시스템의 동작 변화를 주장하는 **비교 주장(Comparative Claim)**에 대해 객관적인 입증 책임을 부여합니다.

---

## 2. 작업 유형별 증거 수집 가이드

### 1) 버그 수정 (`Claim: bugfix`)
- **Before 필수 증거**:
  - 코드를 건드리기 전, 결함이 발생하는 터미널 출력(실패하는 테스트 러너 로그, 오류 스택트레이스, 잘못된 출력 등).
- **After 필수 증거**:
  - 코드 수정 후, 동일한 조건과 입력에서 결함이 재현되지 않고 정상 통과하는 터미널 출력.
- **Before 미확보 시 조치**:
  - 버그 재현 로그 없이 코드만 수정한 경우, Verifier는 결함 해결을 입증할 수 없으므로 해당 항목을 **`[UNOBSERVED]`**로 판정합니다.

### 2) 성능 개선 (`Claim: performance`)
- **Before 필수 증거**:
  - 변경 전 환경에서 측정한 기준 벤치마크 수치 (응답 속도, 메모리 사용량, 처리량 등)와 측정 스크립트/명령어.
- **After 필수 증거**:
  - 동일한 환경 및 측정 도구에서 동일 조건으로 측정한 개선 수치.
- **Before 미확보 시 조치**:
  - 사전 측정 수치 없이 "빨라졌다"고 주장하는 경우, Verifier는 성능 개선을 **`[UNOBSERVED]`**로 판정합니다.

### 3) 신규 기능 (`Claim: feature`)
- 기존 동작이 없으므로 Before 기준선은 불필요합니다 (`N/A`).
- `spec.md`에 명시된 수용 기준(AC)을 증명하는 Fresh Evidence(단위 테스트 통과, 렌더링 관측 증거 등)를 수집합니다.

### 4) 리팩토링 (`Claim: refactor`)
- 기능 변경 없이 구조만 개선하는 작업이므로, Before에 기존 회귀 테스트 통과 로그를 확인하고, After에도 동일한 회귀 스위트가 통과함을 확인합니다.
