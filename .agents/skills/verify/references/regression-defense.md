# 회귀 방어선 원칙 및 테스트 부재 시 대체 가이드 (Regression Defense)

## 1. 회귀 검증의 기본 철학
- **Dijkstra의 테스팅 원칙**: 테스팅은 결함의 존재를 보일 수 있을 뿐, 결함의 부재(0 결함)를 증명할 수 없다.
- 따라서 회귀 테스트 통과가 의미하는 것은 **"실행된 회귀 스위트 범위 내에서 실패가 관측되지 않았다(No failures observed)"**는 사실에 한정된다.
- 이를 "회귀가 전혀 없다"고 과장하지 않고 정직하게 표현한다.

---

## 2. 기존 테스트가 존재하는 경우
1. **변경 영향 분석 (Impact Analysis)**:
   - 이번 변경이 영향을 미치는 공통 모듈, 유틸리티, 인터페이스를 식별한다.
2. **회귀 스위트 실행**:
   - 관련 테스트 스위트 또는 전체 프로젝트 테스트 러너를 실행한다 (`npm test`, `pytest` 등).
3. **무결성 확인 (Test Baseline Preservation)**:
   - 기존 테스트를 단순히 실패를 피하기 위해 임의로 주석 처리하거나, assert를 완화하거나, 삭제하지 않았는지 확인한다.

---

## 3. 기존 테스트가 없는 경우 (3대 대체 방어선)
기존 자동화 테스트가 없는 프로젝트나 레거시 모듈에서도 다음 3대 방어선을 준수한다:

1. **변경 반경(Blast Radius) 엄격 통제**:
   - `plan.md`의 `Target Files`에 선언되지 않은 파일의 무단 수정이 발생하면 결함으로 간주한다.
2. **네이티브 프로젝트 검사(Native Project Checks) 실행 증거**:
   - 프로젝트 환경에 존재하는 applicable checks(빌드, 타입 검사, 린트 등)를 실행하고 무에러 통과 로그를 증거로 제출한다.
3. **명시적 선언 (`[UNOBSERVED]`)**:
   - 기존 테스트 부재 시 `[NO_EXISTING_REGRESSION_SUITE]`를 선언하고, 실행되지 않은 검사는 정직하게 `[UNOBSERVED]`로 명시하여 거짓 통과를 방지한다.
