# Feedback 기록·전달 계약

## 사용 프로젝트 연결

프로젝트의 기존 설치 방식으로 `feedback` Skill과 이 Reference를 함께 사용할 수 있게 한다. Issue 작성 시 `write-issue-pr`, 개선 시 기존 Build/Verify/Review도 사용할 수 있는지 확인한다. 필요한 Skill이 없으면 해당 단계는 보류하고 누락을 알린다. 새 설치 시스템을 만들거나 기존 프로젝트 지침을 덮어쓰지 않는다.

다음 한 문장을 프로젝트 지침에 병합한다.

> OwnHands 사용 중 사용자 교정·Eval 실패·Reviewer Finding을 관측하거나 작업·PR을 종료할 때 `feedback` Skill로 신호 기록과 선별을 수행한다.

기록 경로는 **사용 프로젝트**의 `docs/ownhands/feedback/`이다. 현재 작업의 Target Files/쓰기 권한에 포함된 경우에만 저장한다. 포함되지 않으면 초안을 제시하고 범위 승인을 받는다. 파일 생성과 실제 Git commit은 구분한다.

## capture — 신호 하나당 Markdown 하나

프로젝트 이름을 포함하지 않는 UUID를 한 번 생성해 `<UUID>.md`와 외부 연결에 재사용한다. 같은 신호의 추가 관측이면 기존 ID/파일을 유지한다. 별도 인덱스·DB·스키마 파서는 만들지 않는다.

```markdown
# Feedback: <짧은 문제 제목>

- ID: <uuid>
- 관측일: <ISO 날짜/시간>
- 유형: user-correction | eval-failure | reviewer-finding
- 대상: <관련 OwnHands 자산 또는 unknown>
- OwnHands 버전: <commit/tag 또는 unknown과 사유>
- 작업 근거: <사용 프로젝트의 작업·commit·관련 기록 위치>
- 전달 상태: pending | recorded-only | deferred | linked
- OwnHands Issue: <URL 또는 미등록>

## 관측
- 기대 행동:
- 실제 행동:
- 원본 근거: <최소 발췌 또는 로컬 근거 위치; 비밀값은 저장하지 않음>
- 영향:

## 판단 및 전달
- 원인: <확인된 사실과 가설을 구분>
- 선별 이유:
- 외부 전달용 요약: <내부 식별자·코드·로그를 제외한 최소 재현>
- 처리 기록: <시각, 확인한 Issue/실패/보류 이유>

## 개선 후속
- 사용자 작업 요청: <요청 근거>
- 개선 PR/commit:
- Before/After 및 회귀 Evidence:
- 사용자 채택 결정:
- 사용 프로젝트 적용 버전과 관측:
```

아직 발생하지 않은 항목은 미진행, 확인할 수 없는 버전·근거는 unknown과 사유를 기록한다. 값이나 실측을 지어내지 않는다. 원본 코드·로그·대화는 사용 프로젝트에 남기되 비밀값 자체는 피드백 파일에도 복사하지 않는다. 전달 상태는 Eval의 `PASS / FAIL / UNOBSERVED`와 별개다.

기대 행동은 사용자 요청·승인된 계약의 범위 그대로 기록한다. 예를 들어 실행 금지를 제안 금지로 넓히지 않는다. 명령 제안과 실제 실행, Reviewer의 지적과 확인된 결함을 분리하며 Eval이 FAIL이었다는 관측만으로 그 판정의 정당성까지 확정하지 않는다.

## triage — 선별과 안전한 전달

| 관측 결과 | 처리 |
|---|---|
| 추가 조치 없이 해결 / 제품 자체 버그만 확인 | `recorded-only`, 이유 기록; 제품 버그는 해당 프로젝트에서 처리 |
| 기존 계약을 지켰지만 새 요구가 생김 | 결함이 아닌 개선 제안으로 표시 |
| OwnHands 변경 필요성이 남음 | Issue 후보; 원인 불명이면 조사 후보/가설로 표시 |
| 공개 가능 여부 불명 / 비공개 정보 분리 불가 | `deferred`, 사용자 판단 전 외부 전송 중단 |
| 인증·네트워크·조회 실패 | `deferred`, 원본 보존; 다음 triage에서 재확인 |

공개용 요약에는 OwnHands의 기대/실제 행동과 비공개 정보를 제거한 최소 재현·공유 가능한 근거만 넣는다. 내부 코드·로그·대화·프로젝트 식별자를 그대로 전달하지 않는다. 접근 불가능한 비공개 링크만으로 재현 가능하다고 주장하지 않는다.

### Issue 연결 순서

1. 대상 저장소를 **`taejung3852/OwnHands`**로 명시한다. 사용 프로젝트 기본 remote를 목적지로 쓰지 않는다.
2. 열린/닫힌 Issue에서 `OwnHands-Feedback-ID: <uuid>` 및 관련 자산·기대/실제 행동을 확인한다. 조회가 실패하면 생성하지 않는다.
3. 같은 근본 문제면 기존 Issue에 연결하고 **새 근거가 있을 때만** 공개 가능한 요약을 추가한다. 같은 근거 댓글을 반복하지 않는다. 해결 후 다른 버전에서 재발했다면 버전 차이를 기록한다. 관련성 불명확 시 임의로 병합하지 않는다.
4. 새 문제가 확인되면 기존 `write-issue-pr` Skill로 짧은 Human Brief와 접힌 상세를 작성한다. 상세에 위 ID marker를 포함한다. 기존 Issue에 새 근거를 추가할 때도 해당 ID를 함께 남긴다.
5. 원격 등록/연결이 확인된 뒤 로컬 URL과 `linked`를 기록한다. 생성 응답 유실로 성공 여부가 불명확하면 **ID로 원격 상태를 확인하기 전 재생성하지 않는다**. 조회 결과도 불확실하면 보류한다.
6. 원격 성공 뒤 로컬 저장 실패 시 URL과 저장 미완료를 보고한다. 다음 실행에서 같은 ID로 복구한다. 동시 실행의 원자적 중복 방지는 보장하지 않으며 발견된 중복은 기존 Issue로 연결한다.

Issue 등록·새 근거 추가는 승인된 피드백 흐름에 한한다. 사용 프로젝트에서 그 흐름의 승인이 확인되지 않으면 초안을 제시하고 먼저 확인한다. 이 권한을 비공개 정보 공개, 코드 변경, Push·Merge 권한으로 확대하지 않는다. 무한 재시도로 현재 제품 작업을 지연시키지 않는다.

## follow-up — 구현·평가·채택·다음 사용

- Issue가 생겼다는 이유만으로 수정하지 않는다. 사용자의 명시적 개선 요청과 승인된 Spec/Plan을 기존 Build에 전달한다. 목표·승인 정책 등 계약 변경은 수정 전에 사용자 판단을 받는다.
- 실제 사례의 Before/After와 관련 회귀 Evidence를 연결한다. 제품 버그의 native test와 OwnHands 행동 Eval을 구분한다. 실패를 숨기거나 baseline을 바꿔 성공을 만들지 않는다.
- 사용자가 채택 여부를 결정한다. `FAIL`은 기존 Gate를 차단하며 `UNOBSERVED` 예외는 누락 근거·사유·위험을 보여주고 명시 승인받는다. Push+PR·Merge·Deploy·Cleanup 승인은 서로 승계하지 않는다.
- 채택된 commit/tag와 사용 프로젝트에 적용한 버전·이후 관측을 기록한다. 복사 설치라면 적용 자산과 출처 버전을 남긴다. 적용 방식/권한이 없으면 적용 대기로 남기며 자동 업데이트 시스템을 만들지 않는다. Merge만으로 적용 또는 순환 완료를 주장하지 않는다.

## Review 및 Git 경계

가능한 기록·선별은 최종 Review 전에 끝낸다. 이후 새 Finding이나 Issue URL로 피드백 파일이 바뀌면 일반 diff 변경으로 취급한다. fingerprint에서 제외하지 않으며 다음 외부 Git 동작 전 변경 범위 Review가 필요하다.

작업/PR 종료 후 새 기록은 로컬 변경으로 남기고 완료 보고에 알릴 수 있다. 다음 승인된 commit/Review에 포함한다. 기록을 위해 자동 Push하거나 Merge된 PR을 다시 열지 않는다.
