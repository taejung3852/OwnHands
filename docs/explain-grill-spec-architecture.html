grill-spec: 방금 설계한 핵심 메커니즘 10초 이해

도구를 새로 만들지 않고, GORE와 인터뷰 기법을 얇게 엮은 오케스트레이션(Thin Harness)입니다.

1
Fact(조사)와 Decision(결정)의 엄격한 분리
코드베이스에 이미 있는 팩트는 에이전트가 찾고, 사람은 오직 '결정'만 내립니다.
🤖 에이전트의 책임
Fact Gathering (팩트 탐색)
• 기존 코드베이스 및 설정 직접 검색
• 파일 경로, 함수 시그니처, 의존성 확인
• "코드에 있는 걸 사람에게 되묻지 않는다!"
👤 사람의 책임
Decision Making (의사결정)
• 비목표(Non-goals): "이번에 안 할 것은?"
• 예외 처리 정책: "장애 시 동작 기준은?"
• "사람의 결정을 에이전트가 대신 확정하지 않는다!"
2
작업 규모에 맞춘 3갈래 라우팅 (Route)
모든 기능에 무거운 도구를 강제하지 않고, 작업 성격에 맞게 분기합니다.
Route A: 저장소 없는 단순 아이디어
순수 개념/아키텍처 샤프닝
grill-me / grilling
Route B: 한 세션 일반 기능 (기본 경로) ⭐
grilling 인터뷰 + 코드베이스 팩트 수집
기본 채택 ✅
Route C: 여러 세션이 필요한 거대 과제
태스크 맵 분할 후 intent로 복귀
wayfinder 후보
3
Frontier 인터뷰 & 2단계 Human Gate
인위적인 "3~4개 질문 제한"을 버리고, 2단계 승인으로 스펙을 단단하게 묶습니다.
1. GORE 닻 내리기 ➔ 팩트 탐색 ➔ 프론티어 질문 라운드
🛡️ Checkpoint 1: 사람이 intent.md 승인 (문제 정의 & 비목표 합의)
2. 승인된 Intent 기반 기술 스펙(Spec) 초안 도출
🛡️ Checkpoint 2: 사람이 spec.md 승인 (아키텍처, 엣지케이스, 수용기준)
스스로 확인하는 점검 퀴즈
질문을 읽고 정답 확인 버튼을 눌러보세요!
Q1. 코드베이스에 이미 있는 사실을 에이전트가 사용자에게 질문하는 것이 맞을까요? 정답 확인
💡 틀립니다! Fact(팩트)는 에이전트가 도구로 직접 찾아야 하며, 사용자에게는 오직 사람이 결정해야 할 Decision(비목표, 정책 등)만 질문합니다.
Q2. 일반적인 작은 기능을 만들 때도 Wayfinder를 실행하나요? 정답 확인
💡 아닙니다! Wayfinder는 여러 세션이 필요한 거대 과제용이며, 일반 기능은 Route B(grilling + 팩트 탐색)로 가볍게 처리합니다.
