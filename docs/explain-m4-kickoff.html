2

Before가 없으면 전후 개선을 증명했다고 쓰지 않는다

버그 수정이나 성능 개선은 코드를 고치기 전에 반드시 기존 실패/기준선 수치를 먼저 확보합니다.

2. Build Loop

3

네 가지 검증 책임은 절대 하나로 섞지 않는다

구현 중 자체 루프와 독립 검수자, PR 리뷰와 시스템 평가의 역할을 분리해 자가합리화를 막습니다.

⚡ 3초 점검 퀴즈
Q1. 성능 개선이나 버그 수정 시 코드를 고치기 전에 가장 먼저 해야 할 일은? 정답 확인
A: 'Before 기준선(현재 실패 로그 또는 기준 수치)'을 먼저 확보하는 것입니다. 기준선 없는 사후 비교는 가짜 개선으로 간주합니다.
Q2. Verifier 서브에이전트가 코드를 직접 고치지 않고 read-only로 남는 이유는? 정답 확인
A: 구현자 편향(자기가 짠 코드를 스스로 합리화)을 차단하기 위함입니다. 증거와 수용 기준을 독립적으로 대조하여 정직한 PASS / FAIL / UNOBSERVED를 판정합니다.
