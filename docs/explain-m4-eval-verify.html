⚡ 스스로 풀어보는 3초 퀴즈
Q1. 버그 수정 후 테스트가 다 통과했지만 Before 결함 로그가 없다면 Verifier의 판정은? 정답 확인
💡 UNOBSERVED 입니다! Before 재현 로그가 없으면 에이전트가 실제로 결함을 해결했는지 사후 통과만으로는 입증할 수 없기 때문입니다.
Q2. Fresh Evidence는 오직 CLI 터미널 텍스트 로그만 인정되는가? 정답 확인
💡 아닙니다! UI/레이아웃 스크린샷, DOM 관측, 린트/타입 무에러, 벤치마크 등 작업 성격에 부합하는 모든 '적용 가능한 신선한 증거(applicable Fresh Evidence)'가 인정됩니다.
🛠️ 엔지니어링 투명성 및 실측 세부 사항 (M5 연계)

쉽게 그리느라 생략한 기술적 전제:

  • Verifier는 read-only 샌드박스에서 구동되므로, 무거운 테스트 러너를 직접 재실행하여 쓰기 권한 충돌을 내기보다 구현자가 수집한 Fresh Evidence의 진위와 AC 대조를 수행하는 독립 감사관(Auditor) 모델을 채택합니다.
  • Git 커밋 해시는 검증 증거의 provenance(출처 추적) 역할을 수행하지만, uncommitted 작업 트리 상태에서도 유효한 Fresh Evidence가 관측되면 판정을 진행할 수 있도록 완화되었습니다.

V2-M5 (Continuous Evals) 확장 시사점:

  • M5에서는 `spec.md`의 AC와 `plan.md`의 Fresh Evidence 블록을 JSON/YAML 머신 판독 구조체로 자동 파싱하는 AC Traceability Runner 도입을 검토합니다.
  • 버그 수정 시 Before 재현 로그를 `scratch/`에 자동 스냅샷하는 파이프라인 연계를 검토합니다.
