codex exec 비대화형 구동 및 Runtime Judge

단일 Source of Truth에 기반한 실측 및 3-State 엄격 판정 파이프라인

1

왜 일반 stdout 대신 codex exec --json 인가?

일반 텍스트 파싱은 취약합니다. 공식 --json 플래그를 통해 구조화된 JSONL 이벤트 스트림을 수집하여 기계 판독합니다.

Input codex exec --json --sandbox read-only "프롬프트"
Events thread.started ➔ item.created ➔ turn.completed
Detect 파일 수정 감지 / 커맨드 실행 감지 / 에이전트 출력 누적
2

FAIL과 UNOBSERVED의 엄격한 판정 경계

"환경 부재"를 제품 실패로 오인하지 않습니다. 실행 미개시와 실행 후 결함을 철저히 분리합니다.

👁️ UNOBSERVED

• codex CLI 바이너리 부재

• 인증/환경 미구성으로 실행 미개시

➔ 개발 환경 상태 (품질 실패 아님)

❌ FAIL

• 무단 파일 수정(Mutation) 발생

• 계약 위반 어휘/형식, 세션 타임아웃

➔ 에이전트 제품 결함 (회귀 차단)

3

task-set.json 선언형 runtime_contract 동적 해석

JS 러너에 하드코딩하지 않습니다. task-set.json에 정의된 계약을 런타임에 동적으로 대조합니다.

EVAL-0001 P1-P5 5대 시나리오 출력 계약 및 gh 생성 명령 금지
EVAL-0002 PASS/FAIL/UNOBSERVED 어휘 필수, PARTIAL PASS 금지
EVAL-0003 1차 출처 URL(http/https) 인용 및 사실/공백 분리
EVAL-0005 Verifier 7개 AC 감사 총괄 판정(UNOBSERVED) 일치
4

정직한 관측: 내부 라우팅 추정 금지

이벤트에서 보이지 않는 "내부 스킬 선택"을 자의적으로 추정하지 않습니다. "그 프롬프트에 기대한 행동/출력을 올바르게 완수했는가?"로 판정합니다.

금지된 접근 "이 모델이 내부적으로 write-issue-pr을 골랐을 것이다" (추정 ❌)
OwnHands 원칙 실제 출력에 3칸 규격(무엇/왜/리뷰)이 존재하는지 확인 (실측 ✅)
