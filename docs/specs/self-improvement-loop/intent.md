# Intent: 사용 프로젝트의 피드백을 통한 OwnHands 자기개선

- **작성자**: 박태정 (@taejung3852) & Codex
- **일자**: 2026-09-20
- **상태**: Approved — 사용자 확인 (2026-09-20)
- **관련 Research Issue**: [#150](https://github.com/taejung3852/OwnHands/issues/150)
- **상위 마일스톤**: [V2-M7 — Maintain & Closed Loop](https://github.com/taejung3852/OwnHands/milestone/20)
- **선행 Research**: [M7 Research](../../research/m7-maintain-closed-loop.md)

## 1. 문제 및 배경 (Why)

- **현재 상황과 고통**:
  - 다른 프로젝트에서 OwnHands를 사용하며 생긴 사용자 교정, Eval 실패, Reviewer Finding이 해당 작업 안에 머물면 OwnHands의 지침·Skill·검증 방식 개선으로 이어지지 않는다.
  - 신호를 발견할 때마다 곧바로 자기개선을 시작하면 사용자가 수행하던 프로젝트 작업의 범위와 시간이 늘어난다.
  - 피드백을 기록하거나 Issue를 만드는 것만으로는 개선 효과가 입증되지 않는다. 실제 수정, 평가, 채택, 다음 사용까지 연결돼야 한다.
- **대상 사용자**: OwnHands로 다른 프로젝트를 개발하면서 개선 작업의 우선순위와 채택을 직접 결정하려는 개발자.
- **목표 해석**: M7의 개선 대상은 OwnHands 자신의 개발 수행 방식이다. 사용 프로젝트는 실제 신호가 발생하는 현장이다. 선행 Research의 'OwnHands 자체 피드백부터 시작'이라는 후보보다 이후 사용자 인터뷰의 이 목표를 우선한다.

## 2. 목표 결과 및 가치 (What)

> **다른 프로젝트에서 OwnHands를 사용하며 얻은 실제 신호를 근거로 OwnHands를 수정·평가하고, 사람이 채택한 개선을 다음 사용에 반영하는 자기개선 순환을 만든다.**

### 합의한 흐름

```text
사용 프로젝트에서 OwnHands로 개발
  → 사용자 교정 · Eval 실패 · Reviewer Finding 관측
  → 사용 프로젝트의 docs/ownhands/feedback/에 Markdown 기록
  → 작업 또는 PR 종료 시 선별
  → OwnHands 저장소의 Issue에 등록·연결
  → 사용자가 해당 개선 작업을 명시적으로 요청
  → 원인 확인 · OwnHands 수정 · Eval 비교 및 회귀 확인
  → 사용자 채택 결정
  → 개선된 OwnHands를 사용 프로젝트에서 다시 사용
```

### 달성하고자 하는 결과

- **G-01 — 신호 보존**: 사용자 교정과 Eval 실패·Reviewer Finding을 원본 근거와 함께 기록한다. 신호와 확인된 결함을 구분한다.
- **G-02 — 개선 작업 연결**: 작업·PR 종료 시 남은 개선 필요성을 선별하고 OwnHands Issue에 연결해 사용자가 우선순위를 정할 수 있게 한다.
- **G-03 — 명시적 착수**: Issue 등록 자체로 구현을 시작하지 않는다. 사용자가 작업을 요청한 뒤 기존 계약 안의 수정·검증까지 수행한다.
- **G-04 — 개선 입증과 채택**: 관련 사례에 대한 변경 전후 행동과 기존 동작의 회귀를 평가하고, 사용자가 구체적인 결과를 보고 채택한다.
- **G-05 — 다음 사용 연결**: 어떤 OwnHands 변경이 채택됐고 이후 사용에 반영됐는지 추적할 수 있게 한다.

### 성공 기준

- 실제 사용 프로젝트의 신호에서 OwnHands Issue와 수정·검증 결과까지 근거를 따라갈 수 있다.
- 신호 수집과 Issue 등록이 현재 프로젝트 작업 중 무단 자기개선으로 이어지지 않는다.
- 적어도 하나의 실제 사례에서 신호 → Issue → 명시 요청 → 수정·평가 → 채택 여부의 흐름을 확인한다. 채택한 경우 이후 사용 버전으로의 연결도 확인한다.
- 원래 실패가 해소됐다는 증거와 관련 회귀 검사 결과를 제시한다. 수정·Issue·테스트의 개수만으로 개선을 주장하지 않는다.
- 개선되지 않았거나 검증할 수 없는 결과도 그대로 남기고, 사용자 판단 없이 채택하지 않는다.

## 3. 비목표 (Non-goals & Boundaries)

- 사용 프로젝트의 모든 제품 버그를 OwnHands 결함으로 취급하거나 중앙에서 해결하는 범용 이슈 관리 시스템
- 전체 실행 기록에서 요청받지 않은 문제를 무제한 발굴하는 상시 감시
- 신호 발견 또는 Issue 생성만으로 시작하는 자동 구현, 자동 Merge·Deploy
- 사용자 승인 없이 목표·계약·승인 정책을 변경하는 자기수정
- 수집 단계에서 모든 프로젝트의 전체 Runtime Eval을 재실행하는 방식
- 모델 가중치 학습, 별도 피드백 DB·Dashboard·범용 orchestration framework
- 이번 Intent 작성 단계에서 Skill·Hook·Runner를 구현하거나 특정 구현 수단을 확정하는 것

## 4. 핵심 제약 조건 (Constraints)

- **C-01 — 기록 위치**: 신호 Markdown은 사용 프로젝트의 `docs/ownhands/feedback/`에 두고 해당 프로젝트의 Git으로 버전 관리한다. 파일 구분과 디렉터리 세부 구조는 설계에서 정한다.
- **C-02 — 원본과 작업의 역할 구분**: Markdown은 원본 신호·근거, OwnHands Issue는 해결할 문제·근거 링크·진행 상태를 맡는다. Git 버전 관리는 Markdown과 코드에 적용되며 Issue를 Git 파일처럼 취급하지 않는다.
- **C-03 — 선별과 중복**: 이미 해결되어 추가 조치가 없는 것은 기록으로 남기고, 같은 문제가 있으면 기존 Issue에 연결한다. 새로운 Issue 수를 성과로 삼지 않는다.
- **C-04 — 착수·채택 분리**: 작업·PR 종료 시 Issue 등록과 개선 구현의 시작은 별개다. 명시 요청 후 수정·검증하며, 채택은 사용자가 결정한다.
- **C-05 — 계약 경계**: 기존 계약 안의 개선을 수행한다. 목표·승인 정책 등 계약 변경이 필요하면 수정 전에 사용자에게 묻는다. 기존 Build·Verify·Review와 외부 상태 변경 승인 경계를 재사용한다.
- **C-06 — 증거 무결성**: 원인 추정, 확인된 결함, 개선 효과를 구분한다. `FAIL / UNOBSERVED`를 숨기거나 평가 기준·baseline을 바꿔 개선으로 보이게 하지 않는다.
- **C-07 — Thin Harness**: 기존 Markdown·Git·GitHub Issue·Skill·M5 평가 자산을 우선 재사용한다. 신호 수집, 분류, 개선 검증에 필요한 최소 연결을 설계한다.
- **C-08 — 사용자 결정과 공식 사실 분리**: 위 흐름은 사용자와 정한 OwnHands의 제품 방향이다. Codex가 이를 자동 제공하거나 공식적으로 요구한다고 주장하지 않는다.

### Spec에서 정할 항목

- 사용 프로젝트에 수집 절차를 연결하는 방법과 작업·PR 종료 시점의 감지 방법
- 최소 신호 필드, 파일 단위, 원인 관련성·중복 판단 및 Issue 연결 표시
- 비공개 사용 프로젝트의 근거를 OwnHands Issue에 전달하는 범위와 접근 불가 링크 처리
- GitHub 접근·등록 실패, 종료 절차 재실행 때의 재시도·중복 방지
- 수정 전후 비교에 사용할 사례와 관련 회귀 범위, 채택된 OwnHands 버전의 배포·적용 방식

이 항목들은 기술 설계에서 구체화할 사항이며, 현재 구현 방식이나 새로운 승인 정책을 확정한 것이 아니다.
