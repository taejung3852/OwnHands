# DevHarness 향후계획 및 구현 에이전트 실행 지시문

- **문서 상태:** 구현 착수용 로드맵 초안
- **작성 기준일:** 2026-09-03
- **대상:** DevHarness 레포지토리 생성부터 Milestone·Issue 관리와 구현까지 담당할 에이전트
- **선행 문서:** `Dashboard_layer.md`, `Control_layer.md`, `Design_Rationale.md`
- **제품명:** DevHarness는 가제다. 이름 변경 전까지 작업 식별자로 사용한다.

> 이 문서의 목적은 기능을 한 번에 코딩하라는 것이 아니다. 전체 제품 범위를 잃지 않으면서, 기술적으로 검증 가능한 순서로 레포지토리·Milestone·Issue를 구성하고 각 단계의 Evidence를 남기며 실행하게 하는 것이다.

---

## 1. 구현 에이전트의 최상위 명령

1. 세 선행 문서를 전부 읽고 서로 충돌하는 요구사항을 먼저 찾는다.
2. 사용자에게 이미 확정된 제품 목적과 범위를 다시 처음부터 질문하지 않는다.
3. 구현에 필요한 라이브러리·저장 형식·세부 알고리즘은 먼저 조사하고 추천안을 제시한다.
4. Codex의 현재 동작은 공식 문서와 재현 가능한 probe로 확인한다.
5. 기술적으로 확인되지 않은 사항을 확정 기능처럼 작성하지 않는다.
6. 전체 기능 범위를 GitHub 상위 Issue에 보존한다. Milestone을 나누더라도 기능을 삭제하거나 잊지 않는다.
7. 각 Issue는 수용 기준, 필요한 Evidence, 의존성, Non-goal을 가진다.
8. 구현 완료를 주장하기 전에 테스트와 Evidence를 확인한다.
9. 새로운 기능을 임의로 추가하지 않는다. 필요하면 Issue와 `Design_Rationale.md` 변경안을 먼저 제출한다.
10. HWPX Agent Plugin을 첫 도그푸딩 대상으로 사용하되 DevHarness Core를 HWPX 전용으로 만들지 않는다.

## 2. 레포지토리 생성 지침

### 2.1 생성 조건

- 기존 DevHarness 레포가 없으면 가제 `devharness`로 생성한다.
- GitHub owner와 visibility는 외부 변경이므로 현재 컨텍스트에서 확인할 수 없을 때만 사용자에게 묻는다.
- 기본 branch는 `main`으로 한다.
- 초기에는 제품 문서와 Spike 결과를 우선 commit한다.

### 2.2 첫 Commit에 포함할 문서

```text
docs/
├─ product/
│  ├─ Dashboard_layer.md
│  ├─ Control_layer.md
│  ├─ Design_Rationale.md
│  └─ 향후계획.md
├─ adr/
├─ spikes/
└─ dogfooding/
```

소스 디렉터리 구조와 언어는 Technical Spike와 ADR 이후 확정한다. 문서만 보고 임의로 monorepo, framework, database를 먼저 선택하지 않는다.

## 3. 전체 범위 상위 Issue

레포 생성 직후 다음 상위 Issue를 만든다.

### Issue: `DevHarness 전체 제품 범위 추적`

목적:

- 문서에서 합의한 기능이 Milestone 분할 과정에서 누락되지 않게 한다.
- 각 기능의 구현 상태와 Evidence 준비 상태를 추적한다.

체크리스트:

- Managed Task / Imported Task
- Project Context Profiler
- Adaptive Preflight Interview
- Project Baseline / Task Overlay
- Control Profile Compiler / Lint / Preview
- Codex Adapter
- Config·AGENTS·Rules·Hooks·Sandbox·Approval 관리
- Control Validation
- Canonical Event Log / Projection
- Evidence Store / Redaction
- Guarantee Matrix / Task Guarantee Report
- Workspace Restore Point
- Impact Analysis
- Test Design Guide
- Regression Gate
- Task Review Page
- Feature Validation Page
- Harness Status Page
- Audit & History
- Usage & Cost Analytics
- HWPX Agent Plugin 도그푸딩
- Superpowers Skill 선택적 Vendoring
- Codex 외 Adapter 확장 조건

각 항목은 실제 하위 Issue에 링크한다. `계획됨`만 표시하지 말고 `Blocked by Evidence`, `In Progress`, `Verified`, `Deferred` 상태와 이유를 남긴다.

## 4. 개발 원칙

### 4.1 Vertical Slice 우선

UI만 먼저 완성하거나 Core만 장기간 고립해 만들지 않는다. 각 Milestone은 가능한 경우 다음 흐름의 얇은 수직 단면을 만든다.

```text
실제 Event
→ Evidence 저장
→ Guarantee 판정
→ Dashboard 표시
→ 사용자 검토
```

### 4.2 Evidence before Claim

- 파일 생성은 `Configured`만 증명한다.
- 현재 실행에서 읽혀야 `Loaded`다.
- 실제 경계를 강제한 probe가 있어야 `Enforced`다.
- 관찰할 수 없으면 `Unobserved`다.

Issue 완료 기준도 이 상태를 구분한다.

### 4.3 Build Order는 Evidence 의존성으로 결정

Dashboard의 전체 화면 범위는 유지하되, 실제 데이터를 제공할 Core와 Adapter가 없는 화면을 하드코딩된 성공 상태로 만들지 않는다.

### 4.4 테스트 전략

- 기능·버그 구현은 test-first workflow를 적용한다.
- 테스트 종류는 Test Design Memo에서 선택한다.
- 새 기능 테스트와 회귀 테스트를 분리한다.
- 완료 전 `verification-before-completion` 성격의 독립 확인을 수행한다.
- HWPX fixture와 실제 문서 샘플의 차이를 명시한다.

## 5. Milestone 개요

| Milestone | 목표 | 종료 시 확인 가능한 상태 |
|---|---|---|
| **M0 — Product & Technical Baseline** | 레포·문서·ADR·Technical Spike 준비 | 구현 경로와 보장 경계가 문서화됨 |
| **M1 — Evidence Core** | Task·Event·Evidence·Guarantee 최소 코어 | 실제 사건이 저장되고 주장 판정 가능 |
| **M2 — Control Profile Lifecycle** | Profiler·Interview·Contract·Preview·Apply | 작업별 실행 계약을 만들고 검토 가능 |
| **M3 — Codex Managed Task Integration** | Codex Desktop 우선 연결과 통제 Validation | 실제 작업에서 설정·이벤트·승인을 추적 |
| **M4 — Assurance Pipeline** | Impact·Test Design·Regression Gate·Restore | 완료 주장에 근거 기반 Gate 적용 |
| **M5 — Dashboard Vertical Product** | Task Review·Harness Status·Feature Validation | 사용자가 실제 작업을 이해·검증·판단 |
| **M6 — HWPX Dogfooding & Evaluation** | 실제 HWPX 작업 반복 사용과 개선 | 사람 병목 감소 Evidence 확보 |
| **M7 — Packaging, Quality & Release** | Plugin 패키징·문서·테스트·오픈소스 준비 | 재현 가능한 설치와 사용 가능 |
| **M8 — Optional Expansion** | Usage Analytics·추가 Adapter | 핵심 안정화 후 확장 |

Milestone 이름과 번호는 GitHub 생성 시 유지한다. 단, Technical Spike 결과로 의존성이 달라지면 ADR과 이유를 남기고 순서를 조정할 수 있다.

## M0 — Product & Technical Baseline

### 목표

구현 전에 현재 Codex 통합 경로와 DevHarness의 보장 범위를 검증한다.

### 필수 Issues

#### M0-01 `제품 문서 기준선 등록 및 충돌 검사`

작업:

- 네 문서를 레포에 등록
- 용어 사전 작성
- 문서 간 책임 중복·충돌 검사
- 확정·추천·Technical Spike 구분

수용 기준:

- Control과 Dashboard 책임이 중복 없이 연결됨
- LangGraph 전용 표현이 없음
- HWPX가 도그푸딩 대상일 뿐 Core 요구사항이 아님을 명시
- Preflight 토큰·비용 기능이 없음

#### M0-02 `Codex Desktop 통합 경로 Spike`

비교:

- App Server
- SDK
- Hooks
- Config·Rules·AGENTS 파일 관리
- 실행 로그·Event 관찰

검증 질문:

- Desktop thread/turn event에 접근 가능한가
- approval request와 result를 관찰할 수 있는가
- Hook started/completed를 확인할 수 있는가
- active config source를 확인할 수 있는가
- 기존 Desktop UX를 유지할 수 있는가
- 실험적 기능에 의존하는 범위는 어디까지인가

산출물:

- `docs/spikes/codex-desktop-integration.md`
- ADR: 선택한 통합 경로와 대안
- 실행 가능한 최소 probe

#### M0-03 `Control Validation 가능 범위 Spike`

검증 대상:

- config loading
- AGENTS instruction source
- Rules match/enforcement
- Hooks invocation·timeout·failure
- Sandbox filesystem/network
- Approval Policy
- config precedence·conflict
- MCP/Plugin discovery
- Unobserved paths

수용 기준:

- 각 항목에서 `Configured / Loaded / Enforced / Observed / Unobserved`를 판정할 방법이 문서화됨
- 안전한 probe와 금지할 probe가 구분됨
- fail-open 가능성이 기록됨

#### M0-04 `Guarantee Matrix v1 작성`

작업:

- `Control_layer.md` 초기 Matrix를 machine-readable schema로 옮길 수 있는지 검토
- Claim ID 부여
- Required Evidence, Forbidden Wording, Remaining Risk 정의
- Task Guarantee Report 예시 작성

수용 기준:

- 최소 10개 핵심 Claim이 실제 Evidence 조건과 연결됨
- 전체 안전·완전성을 주장하는 문구가 없음
- Imported Task에서 사용할 수 없는 Claim이 구분됨

#### M0-05 `Superpowers Skill Vendoring Spike`

작업:

- 사용할 Skill 후보 검토
- `using-superpowers`와 bootstrap 제외 검증
- MIT License와 고지 방식 확인
- namespace 전략
- upstream commit pin
- behavior test 전략

산출물:

- ADR
- `THIRD_PARTY_NOTICES.md` 초안
- Vendoring 대상 목록과 제외 이유

### M0 종료 Gate

다음이 없으면 M1 구현을 시작하지 않는다.

- Codex 통합 ADR
- Control Validation 표
- Guarantee Matrix v1
- Event/Evidence 저장 결정
- Superpowers Vendoring 결정

#### M5-09 `Dashboard 전체 범위 추적 검증`

## 6. Issue 작성 규칙

모든 구현 Issue는 다음 형식을 따른다.

```markdown
## 목적
사용자 문제와 이 Issue가 해결하는 병목

## 범위
이번 Issue에서 구현할 것

## Non-goals
이번 Issue에서 하지 않을 것

## 의존성
선행 Issue / ADR / Evidence

## 설계 제약
관련 제품 문서와 Guarantee 규칙

## 수용 기준
관찰 가능한 완료 조건

## 필요한 Evidence
Configured / Loaded / Enforced / Observed 중 무엇이 필요한지

## 테스트
기능 테스트 / 회귀 테스트 / 실패 경로

## 문서 변경
ADR, Design Rationale, 사용자 문서
```

Issue를 닫기 전에 수용 기준과 Evidence를 실제 결과로 갱신한다. 단순히 PR이 merge됐다는 이유로 완료 처리하지 않는다.

---

## 7. Pull Request와 Review 원칙

- 한 PR은 하나의 명확한 Issue를 해결한다.
- 기능 변경과 대규모 무관 리팩터링을 섞지 않는다.
- PR 본문에 변경 기능, 연관된 기능, 테스트, 미검증 영역을 쓴다.
- 자동 생성 요약을 그대로 신뢰하지 않고 Evidence link를 포함한다.
- 새 schema와 Event에는 migration·compatibility 전략을 포함한다.
- 완료 전 독립 verification을 수행한다.

- Projection architecture

- Control Profile merge/precedence
- Impact Analysis engine
- Test runner integration
- Dashboard framework

## 9. 중단·재설계 조건

다음이 발생하면 기능 추가를 멈추고 설계를 재검토한다.

- Configured를 Enforced로 신뢰할 방법이 없음
- Codex Desktop에서 필요한 핵심 Event를 관찰할 수 없음
- Hook failure가 통제 공백을 만들지만 Dashboard가 감지하지 못함
- DevHarness 오버헤드가 사람 검토 절감보다 큼
- Impact Analysis가 과도한 오탐으로 사용자를 다시 병목에 빠뜨림
- Dashboard Summary와 raw Evidence가 반복적으로 불일치
- HWPX 전용 구현이 Core에 침투
- 외부 Superpowers 업데이트가 DevHarness Router를 깨뜨림

재설계 시 Issue를 닫지 말고 실패 Evidence와 학습을 남긴다.

## 10. 최종 제품 완료 기준

DevHarness의 첫 안정 버전은 다음을 만족해야 한다.

1. Managed Task가 Preflight와 Contract 없이 시작되지 않는다.
2. Codex 설정과 통제가 실제로 로드·집행됐는지 구분한다.
3. Hooks, Sandbox, Approval Policy, Rules, 설정 충돌과 Unobserved를 검증한다.
4. Event와 Evidence가 작업·Worktree별로 추적된다.
5. Guarantee Matrix 기준으로 Task Guarantee Report를 생성한다.
6. Impact Analysis가 연관된 기능과 검증 범위를 제시한다.
7. Regression Gate가 작업별 기준으로 Pass/Soft/Hard를 판정한다.
8. Dashboard에서 기능 변화·연관 기능·검증·통제·잔여 위험을 이해할 수 있다.
9. 사용자가 HWPX 기능을 직접 검증하고 결과를 Evidence로 남길 수 있다.
10. Raw Evidence는 로컬에 유지되고 공유 리포트는 마스킹된다.
11. 도그푸딩에서 사람의 이해·검토 병목 감소를 측정한다.
12. 기능 목록과 실패 사례가 GitHub Issue와 문서에서 누락되지 않는다.
