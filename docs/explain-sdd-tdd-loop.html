왜 회사의 필수 검증사항은 배포 전에 누락되는가?

기존 SDD의 문서 박제화와 TDD의 터널 시야를 깨부수는 1:1 강제 연결선

1
단독 SDD와 단독 TDD가 실패하는 이유
스펙은 실행되지 않아 방치되고, TDD는 자기가 아는 쉬운 것만 테스트합니다.
⚠️ 기존 SDD의 고질적 결함
  • • 비실행성 (Non-executable): 문서는 컴파일/자동실행되지 않아 방치됨
  • • 체크리스트 눈속임: 바쁘면 읽지도 않고 "검토완료" 체크
  • • 에이전트 환각: 코드가 예외를 못 다뤄도 "준수했다"고 거짓말
⚠️ 기존 TDD의 고질적 결함
  • • 터널 시야: 자기가 생각 못한 회사 규칙은 테스트조차 안 짬
  • • 해피패스 편향: 복잡한 엣지케이스는 빼고 쉬운 것만 통과
  • • Mock 잔치: 가짜 객체로 100% 통과시키고 실운영서 폭발
2
검증 누락을 원천 차단하는 3대 연결선
스펙의 수용 기준을 기계적 테스트 경로와 1:1로 묶고, 제3자 검증자로 인가합니다.
1
Acceptance Criteria 1:1 테스트 매핑
spec.md의 모든 수용 기준/엣지케이스에 테스트 파일·함수를 필수 할당
스펙 누락 방지
2
Red(실패) 사전 증거 확보
코드 구현 전, 테스트가 먼저 실패하는 터미널 출력을 근거로 고정
사후 조작 차단
3
독립 Verifier (read-only) 최종 대조
구현 에이전트와 격리된 검증자가 spec.md 기준선 전량 역추적 판정
자가합리화 봉쇄
3
인간의 고민 흔적(ADR)은 spec.md와 물리적으로 분리한다
기계용 명세서(spec.md)의 노이즈를 원천 차단하고, 생각의 궤적은 decision.md에 독립 보존합니다.
📄 spec.md (AI 에이전트·검증기용 기술 청사진)
엄밀한 요구사항·수용 기준만 담아 노이즈 제로 유지 (컨텍스트 오염 및 환각 방지)
Noise-Free
📝 decision.md (인간 엔지니어용 고민 흔적 및 결정 일지)
고려했던 대안, 버린 이유, 트레이드오프 기록 (선택적 작성으로 문서 피로도 방지)
Thought Trail
💡 스스로 풀어보는 3초 퀴즈
Q1. 모든 단위 테스트가 초록색(PASS)인데도 현업에서 장애가 나는 주된 이유는? 정답 확인
👉 TDD는 개발자가 생각한 코드만 테스트하므로, 회사의 필수 비즈니스 규칙이나 엣지케이스가 스펙에서 테스트 코드로 연결되지 않고 애초에 누락되었기 때문입니다.
Q2. 왜 고민의 흔적(ADR)을 spec.md 본문에 직접 넣지 않고 분리하나요? 정답 확인
👉 에이전트가 코드를 구현할 때 버린 대안이나 장황한 인간의 고민 과정을 읽으면 컨텍스트 토큰이 낭비되고, 무엇이 진짜 구현 요구사항인지 헷갈려 환각(탈선)을 일으키는 직접적인 노이즈가 되기 때문입니다.
🛠️ 엔지니어링 세부 사항 및 원문 근거 (Detailed Context)
  • 문서 역할 분리: spec.md는 기계가 읽는 건조한 명세서로 순도를 지키고, decision.md는 인간이 설계 갈림길에서 고민한 맥락을 남기는 독립 아티팩트로 관리합니다.
  • 선택적 작성: 모든 사소한 작업에 decision.md를 강제하지 않으며, 설계 트레이드오프가 컸던 작업에만 작성하여 문서 오버헤드를 막습니다.
  • 근거 자료: ADR-0004 (intent/spec 규격) · M3 킥오프 설명
