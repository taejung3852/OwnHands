# 프로젝트 여정 — OwnHands는 어떻게 여기까지 왔는가

> 상태: **편집 초안** (사용자 검토 전)
> 이 문서는 개발자 박태정의 실제 작업 과정과 판단 변화를 정리한다. 제품 홍보 문서가 아니다.
> 직접 인용은 인용 블록으로, 편집한 설명은 본문으로 구분한다.

---

## 1. 시작 — AI가 만든 결과를 사람이 믿을 수 있는가

OwnHands는 AI 코딩 에이전트가 만든 결과를 사람이 이해하고 검증하면서 개발을 주도할 수 있는 도구로 시작했다.

출발점이 된 질문은 하나였다.

> AI가 만든 작업이 정말 요구를 만족했는가?
> 무엇을 확인했고 무엇을 확인하지 못했는가?
> 사람이 어떤 근거를 보고 판단해야 하는가?

이 질문은 "AI를 못 믿겠다"는 뜻이 아니었다. **위임한 작업의 결과를 사람이 판단하려면 판단할 근거가 있어야 한다**는 문제의식이었다.

> 정확한 최초 프로젝트 사례, 시작 날짜, 총 개발 기간은 이 문서를 만든 시점에 확정하지 않았다.
> 확인되지 않은 시점·기간·성과를 서술에 채워 넣지 않는다.

---

## 2. V1 — 검증을 구조로 만들다

V1은 위 질문에 **구조로** 답하려 했다. 실제로 구현해 저장소에 남은 것들이다.

| 구성 | 답하려던 질문 |
|---|---|
| Issue | 이 작업은 무엇을 만족해야 하는가? |
| Verification Spec | 무엇을 확인해야 완료라고 할 수 있는가? |
| Baseline | 변경 전 상태는 어땠는가? |
| Review | 변경 후 요구가 충족됐는가? |
| Evidence | 그 판단의 근거는 어디에 있는가? |
| Dashboard | 사람이 이것을 어떻게 한눈에 이해하는가? |

핵심 의도는 일관됐다. **기록된 검증 결과와 실제 근거를 연결하고, 실패·미확인·오래된 결과를 성공처럼 표현하지 않는 것.**

이 의도는 상태 어휘에도 그대로 남아 있다.

```text
Claim:      verified / failed / inconclusive / unobserved
Review:     ready / needs-review / blocked
Freshness:  current / stale / unknown
```

`unobserved`와 `unknown`이 1급 상태로 존재한다는 점이 이 프로젝트의 성격을 보여준다.
**모르는 것을 모른다고 표시할 자리를 먼저 만들었다.**

V1에서 실제로 구현하고 병합한 범위는 [V1 기록](../history/v1.md)에 정리한다.

> ⚠️ **V1은 완료 상태에서 끝나지 않았다.** 주요 흐름은 구현·병합했지만 통합 수용 검증([#99](https://github.com/taejung3852/OwnHands/issues/99))은 **실행하지 않은 채** V2로 전환했다. 실행하지 않은 계획을 결과로 기록하지 않는다.

---

## 3. 실제 구현하며 한계를 발견했다

이 프로젝트 여정에서 가장 중요한 지점이다.

> **실제 구현하며 한계 발견**

한계는 문서를 읽다가 발견한 것이 아니라 **직접 만들면서** 발견했다.

### 무엇이 일어났는가

사용자는 계획을 세우고 구현의 많은 부분을 코딩 에이전트에 위임했다. 그러나 처음부터 요구사항마다 무엇을 Skill로, 무엇을 Reference로, 무엇을 Agent로, 무엇을 기존 도구로, 무엇을 Script로 해결할지 충분히 나누지는 못했다.

그 결과 이런 것들이 늘어났다.

- 여러 경우를 직접 처리하는 스크립트
- 예외 처리
- 원본과 표현의 정합성 검사
- 서버·캐시·브라우저 상태 관리

Dashboard에서는 부담이 더 분명해졌다. 원래 목적은 "작업을 이해하는 것"이었지만, 실제로 관리해야 했던 것은 접속과 재접속, 생성 시점, polling, 캐시, 페이지 상태, 최신성, 근거와 표현의 일치였다.

사용자는 여기에 많은 체력을 썼다고 설명했다.

> "유지보수 비용이 너무 크고 너무 버거운것 같아."

> "주객전도가 되는 상황 즉, 배보다 배꼽이 더 커지는 현상이 생긴거 같아."

### 핵심 — 무엇이 문제였는가

**원래 원하던 개발 경험보다, 그것을 지원하는 별도 시스템의 운영 부담이 더 커졌다.**

개별 요구를 엄격하게 보장하려 할수록 도구 자체를 유지하는 부담이 커졌다는 것이 사용자의 판단이다.

### 이 경험을 이렇게 읽으면 안 된다

이 한계는 다음 결론이 **아니다**.

- ❌ "보안과 무결성은 필요 없다"
- ❌ "모든 스크립트와 테스트가 잘못됐다"
- ❌ "원인은 전부 모델이나 구현 에이전트 탓이다"

V1의 검증 원칙 자체는 유효했고, 지금도 유지된다.
문제는 원칙이 아니라 **그 원칙을 떠받치기 위해 직접 만들어 운영해야 했던 시스템의 크기**였다.

## 4. Anthropic Playbook — 프로젝트 시작 이후의 전환 계기

핵심 참고 자료: <https://claude.com/blog/the-ai-native-sdlc-playbook>

**시간 순서를 정확히 기록한다.**

| 사건 | 의미 |
|---|---|
| OwnHands의 시작 | AI 개발 결과를 사람이 이해하고 검증하려던 문제의식 |
| V2로의 전환 | 실제 구현의 한계와 Playbook을 통해 구체화된 SDLC 전체·지속 개선 방향 |

사용자는 **OwnHands를 이미 개발하고 있었다.** 이 글을 읽고 OwnHands를 처음 만든 것이 아니다.

이미 개별 검증과 Dashboard에 집중해 고민하던 중에 이 글을 읽었고, 그 고민을 **AI-native SDLC 전체의 구성**이라는 더 큰 틀로 이해하게 됐다.

이 글은 사용자에게 링크 하나짜리 참고문헌이 아니다. 이미 하고 있던 고민을 자세한 구조로 연결해 준 **V2의 핵심 참고 자료**다.

다만 블로그의 모든 구현 예시를 OwnHands의 강제 요구사항으로 복사하려는 것은 아니다.
무엇을 가져오고 무엇을 가져오지 않는지는 [Anthropic Playbook 대응표](../references/anthropic-playbook.md)에 정리한다.

## 5. V2로의 전환 — 무엇을 바꾸기로 했는가

### 책임 하나를 기본 경로에서 덜어낸다

> **"항상 연결된 최신 화면을 제공한다"는 책임을 기본 경로에서 제거한다.**

상시 Dashboard 대신, 사용자가 개발하던 대화에서 **명시적으로 설명 기능을 호출한다.**

> "내가 명시적으로 스킬을 사용해서 현상황을 보는 용도로 사용하는게 나을 것 같아."

요청 시 관련 자료를 읽고, 지금 필요한 내용만 Markdown 또는 HTML로 만든다. 설명 생성 당시의 자료와 한계를 밝히고, **이후 변경을 자동 반영한다고 약속하지 않는다.**

이 선택이 상시 화면 유지에 따라오던 polling·캐시·재접속·최신성 관리 부담을 기본 경로에서 덜어낸다.

### 화면보다 흐름을 먼저 만든다

> "SDLC에대한 구성을 우선 잘하는게 더 중요하다는 생각이들었어."

전체 SDLC가 잘 구성되고 사용자가 Intent·Spec·Plan을 파악할 수 있다면, 별도 상시 Dashboard에 의존할 필요가 줄어든다고 판단했다.

**V2는 프론트 기술을 교체하는 프로젝트가 아니다.** 개발 흐름을 우선하고, 필요한 지침과 평가를 가볍게 연결하는 방향 전환이다.

### 공식 근거를 중심에 둔다

> "항상 중심은 공식문서와 아까 너한테 줬던 anthropic 블로그가 될 거야."

V1에서 직접 만들어 짊어졌던 것 중 상당수는, 실행 플랫폼이 이미 제공하거나 앞으로 제공할 수 있는 영역과 겹칠 수 있다.
그래서 V2는 **만들기 전에 공식 문서를 먼저 확인한다.** 자세한 내용은 [개발 방법](../v2/development-method.md).

### 플랫폼별로 구체적으로 만든다

> "각각 specific하게 하는게 맞다고 판단했어."

모델과 코딩 에이전트마다 형식·기능·권한·제약이 다르다. 공통 분모로 뭉뚱그리지 않고 각각에 맞게 구성한다.
V2의 1차 실행 플랫폼은 **Codex**다.

## 6. 개인 전용으로 제한하지 않는다

> "회사에서 나 이런식으로 업무할 수 있다를 보여줄 수있는 나의 무기인데?"

사용자는 취업을 준비하고 있으며, OwnHands를 통해 회사에서도 사람과 AI가 함께 일하는 방식을 설계하고 설명할 수 있음을 보여주고자 한다.

사용자는 **첫 사용자이지 제품의 유일한 대상은 아니다.** 기본 정책으로 사용할 수 있고, 조직에서는 회사 정책과 실행 환경을 연결하기 쉽게 설계하려 한다.

단, 다음 두 가지는 다르다.

| 사실 | 아직 아닌 것 |
|---|---|
| 조직 적용을 **목표로 한다** | 실제 회사에 도입해 **검증했다** |

아직 없는 기업 적용 성과나 생산성 수치를 만들지 않는다.

---

## 7. 장기 방향

> "내 OwnHands 스킬은 나랑 함께 성장하는 개발 도구가 될거야."

OwnHands의 장기 비전은 완성해서 멈추는 제품이 아니라, **도구와 개발 방식이 함께 계속 개선되는 것**이다.

이 방향이 V2에서 Continuous Evals를 핵심 축으로 두는 이유다. 개발 중인 제품이 나아졌는지뿐 아니라, **제품을 만드는 Agent System 자체가 나아졌는지**를 확인해야 하기 때문이다.

그리고 그 평가를 마지막으로 미루지 않는다.

> "초기에 작은 Eval을 넣고 M5에서 확장 하는 방식으로 가자."
