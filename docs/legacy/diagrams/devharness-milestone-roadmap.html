M0–M8 마일스톤 작업 지도

각 마일스톤에서 무엇을 만들고, 다음 단계로 넘어가기 전에 무엇을 확인하는지 한눈에 읽는 문서입니다. 날짜나 예상 기간이 아니라 제품의 검증 순서를 보여 줍니다.

현재 기준: M0 문서·Spike·ADR 검토 단계. M0 ADR 검토 전에는 M1 기능 구현을 시작하지 않습니다.

Story Map · Overview

전체 제품 이야기

왼쪽에서 오른쪽으로 제품의 능력이 쌓입니다. 위에서 아래의 세 묶음은 기준선, Core, 사용자 제품·검증·출시 범위를 구분합니다.

M0 · Baseline

제품과 기술의 기준을 먼저 고정

구현 전에 Codex 연결 방식, Control 검증 범위, Guarantee 주장 규칙, Event·Evidence 저장 방식을 실제 Probe와 ADR로 결정합니다.

M1 · Evidence Core

실제 사건을 주장 가능한 근거로

Task를 식별하고 Event를 보존한 뒤 Evidence, Projection, Guarantee 판정을 하나의 작은 수직 흐름으로 검증합니다.

M2 · Control Profile

작업별 실행 계약을 만들고 먼저 검토

프로젝트를 분석하고 꼭 필요한 질문만 한 뒤 Baseline과 Task Overlay를 분리해, 적용 전 변경점과 권한 경계를 보여 줍니다.

M3 · Codex Integration

실제 Managed Task에서 통제를 관찰

M0에서 선택한 공식 통합 경로로 작업을 시작하고, 설정·지침·Rules·Hooks·Sandbox·Approval이 실제로 어떻게 작동했는지 구분해 기록합니다.

M4 · Assurance

완료 주장을 회귀 근거와 연결

복구 지점을 남기고 영향 범위를 분석한 다음, 적절한 테스트를 설계해 변경 전후를 비교하고 검증 공백을 찾습니다.

M5 · Dashboard

사람이 이해·검증·판단하는 제품

실제 M3·M4 Evidence만 사용합니다. 결론과 다음 행동을 먼저 보여 주고, Trace와 선택한 Evidence로 두 번 이하의 상호작용 안에 내려갑니다.

M6 · Dogfooding

HWPX로 실제 효용과 실패를 측정

HWPX Agent Plugin은 첫 도그푸딩 대상일 뿐 Core의 전용 목적이 아닙니다. 사용 전후의 사람 병목과 잘못된 자신감을 함께 측정합니다.

M7 · Release

다시 설치하고 검토할 수 있는 제품으로

패키지 구조부터 설치 수명주기, 설정 복구, 라이선스·보안, 통합 테스트, 문제 해결과 schema migration까지 출시 품질을 묶습니다.

M8 · Optional

Core가 안정된 뒤에만 확장

사용량·비용 분석과 추가 Adapter는 선택 사항입니다. 핵심 계약이 Codex 전용 구조에 묶이지 않았다는 Evidence가 먼저 필요합니다.

How to read

이 그림이 말하는 핵심

DevHarness는 UI를 먼저 만드는 프로젝트가 아닙니다. 실제 사건에서 출발해 사람이 최종 판단할 수 있는 근거까지 연결하는 순서가 제품 구조입니다.

제품의 중심 수직 흐름

실제 Event → Raw Evidence → Guarantee 판정 → Dashboard 요약 → 사용자 검토. 어느 단계도 앞 단계의 실제 근거 없이 성공 상태를 만들지 않습니다.

중요한 두 Gate

  • M0 ADR 검토 전 M1 구현 금지
  • M0-07 승인 전 M5 Production UI 금지
