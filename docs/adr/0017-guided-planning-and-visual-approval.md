# ADR-0017: GORE 인터뷰를 단계·미결정 상태·시각 승인으로 안내한다

- 상태: Accepted — ELI5 시점·내용/저장 승인 분리 Spec 사용자 승인 / 구현 미진행
- 일자: 2026-09-22
- 관련: [#154](https://github.com/taejung3852/OwnHands/issues/154), 피드백 2·3·4·10·15
- 관련 결정: [ADR-0011](0011-chat-codex-ownership-and-handoff.md), [ADR-0018](0018-core-and-companion-skills.md), [ADR-0019](0019-github-centered-sdlc-and-stage-commits.md)
- 확정 Spec: [Chat Plan & Design](../specs/chat-plan-design-flow/spec.md), REQ-05~13, REQ-18~21

## Context

사용자는 인터뷰가 얼마나 남았는지 알기 어렵고, 문서 파일명 중심 설명과 긴 불릿 나열만으로는 현재 단계와 승인할 내용을 이해하기 힘들었다. 러프한 요구를 더 구체적으로 논의하고 싶다는 요구도 나왔다. 이후 사용자는 9번의 Chat 중심 기획·설계를 우선하겠다고 했다.

후속 Spec 논의에서 사용자는 Stage 내용 승인 직전 ELI5를 활용하고, 내용 승인과 GitHub 저장 승인을 구분하기로 했다. 이 결정은 매 대화마다 설명 Skill을 호출하거나 새 상태 관리 Runtime을 만드는 것이 아니다.

## 사용자 요구와 확정 방향

- Plan(기획)과 Design(설계)의 시작·검토·승인·완료를 대화에서 드러낸다. 파일명을 주 UI로 요구하지 않되 산출물은 실제로 보존한다.
- 현재 남아 있는 질문/결정을 보여주고 꼬리질문으로 늘어날 수 있음을 반영한다.
- Intent와 Spec 각각의 전체 내용이 검토 가능한 상태가 된 직후, 내용 승인 전에 ELI5로 큰 그림을 보여준다. 인터뷰 중 매번 호출하지 않는다.
- ELI5는 같은 Plugin 내부 Companion Skill이며 별도 MCP 서버를 추가하지 않는다. 원본·revision·license 및 실제 호출은 별도로 확인한다.
- 내용 승인과 GitHub 저장 승인은 별개다. 내용에 동의했다고 GitHub write까지 승인한 것으로 간주하지 않는다.
- Intent는 GORE 기반 목적·성공 기준·비목표를 충분히 논의하고, Spec은 구현 가능한 기술 계약으로 구체화한다.
- 이 UX의 우선 적용 공간은 ChatGPT다. 같은 인터뷰를 Codex에서 의무적으로 다시 수행하지 않는다.

## 단계 승인

```text
Stage 작성 → 검토 준비 → ELI5 시각 요약 → 사용자 내용 승인
→ GitHub 저장 대상 검토 → 사용자 저장 승인
→ 현재 GitHub 상태 재확인 → Stage 산출물 일괄 저장 → 저장 완료 표시
```

문서가 생성됐다는 사실만으로 단계를 완료 처리하지 않는다. 사용자가 승인하는 것은 요약 그림뿐 아니라 그 그림과 일치하는 문서의 특정 상태다.

기획 요약은 목표·비목표·사용자 흐름·핵심 선택을 중심으로 한다. 설계 요약은 구성 요소·데이터 흐름·실패 경로·검증 기준을 중심으로 한다. 기획 승인 전에 미결정 아키텍처를 그림으로 확정된 것처럼 보이지 않게 한다.

## 문서 상태와 저장 상태

문서의 `Approved`는 사용자 내용 승인을 뜻하며 GitHub 저장 여부까지 포함하지 않는다. 별도의 복잡한 상태 머신을 만들지 않고 Chat에서 다음처럼 구분한다.

```text
Intent 승인 완료
GitHub 저장: 대기 / 실패 / 완료
```

GitHub를 사용할 수 없어도 기획·설계 논의 및 내용 승인은 가능하다. 현재 진행 단계의 수동 저장용 파일과 가이드를 제공하며 저장되지 않은 것을 완료로 보고하지 않는다. 다시 연결됐을 때의 자동 복구 대신 현재 상태 재조회·Reconcile을 수행한다.

## 진행 표시 제안과 남은 제한

총 질문 수를 미리 고정하기보다 현재 확인된 미결정 항목과 확정된 결정 수를 표시한다. 꼬리질문으로 새 항목이 생기면 이유와 함께 갱신한다. 정확한 단위·표시 주기는 이번 Spec이 별도 수치로 확정하지 않았다.

사용자가 요청한 남은 시간 안내는 추정 데이터·사용자 응답 대기 처리·재추정 방식이 아직 정해지지 않았다. 근거 없는 카운트다운이나 정확한 완료 시각을 지어내지 않는다. ELI5 호출 시점 확정을 시간 추정 기능 구현 완료로 해석하지 않는다.

## 인터뷰의 깊이

- 질문은 결과를 바꾸는 중요 모호성, 의미 있는 대안, 안전·권한·실패 정책에 집중한다.
- 저장소·도구로 확인 가능한 사실을 사용자에게 반복 질문하지 않는다.
- 이미 명확히 결정한 내용은 유지한다. 미결정 부분만 좁힌다.
- Intent에는 목적·대상·성공 기준·범위를, Spec에는 입출력·인터페이스·상태 전이·실패 처리·AC를 기록한다.
- 영향이 없는 구현 취향까지 모두 승인받는 무한 인터뷰를 목표로 하지 않는다.

## 경계

기존 ELI5 원본을 확인하지 않고 새 자체 Explain/Archify 렌더러로 대체하지 않는다. 실제 Skill 호출, 생성된 시각 자료, 원본 문서와의 일치는 구현·E2E 검증 대상이며 이 ADR 승인만으로 관측됐다고 하지 않는다.
