# ADR-0016: 제품 문서와 OwnHands 피드백을 저장 전에 분류한다

- 상태: 사용자 분리 방향 확정 — 라우팅 상세화·기존 기록 정리 미진행
- 일자: 2026-09-22
- 관련: [#154](https://github.com/taejung3852/OwnHands/issues/154), 피드백 1·7
- 기존 계약: [feedback-contract.md](../../.agents/skills/feedback/references/feedback-contract.md)

## Context

사용자는 Intent 인터뷰 중 제품 정책을 선택한 기록이 ADR 또는 제품 명세 대신 OwnHands feedback 디렉터리에 저장됐다고 보고했다. 별도로 제품 구현의 검증 누락을 recorded-only로 남긴 사례도 있다.

기준 버전의 Feedback 계약은 사용자 교정·Eval 실패·Reviewer Finding을 넓게 수집하고 제품 문제를 recorded-only로 종결할 수 있게 되어 있다. 따라서 새 요구는 에이전트의 파일 경로 실수만 수정하는 것이 아니라 수집 대상과 기록의 역할을 좁히는 정책 변경이다.

## 사용자 확정 방향

OwnHands 피드백 디렉터리는 OwnHands의 행동·지침·도구 사용 경험과 개선 신호를 다룬다. 제품의 모든 질문·정책 선택·버그를 이곳에 복사하지 않는다. 분류한 다음 적절한 기록을 생성한다.

## 분류 계약 제안

| 내용 | 주된 기록 | OwnHands Feedback 여부 |
|---|---|---|
| 제품이 무엇을 해야 하는가 | 제품 intent.md / spec.md | 원칙적으로 아님 |
| 중요한 대안 중 무엇을 왜 선택했는가 | 제품 ADR | 원칙적으로 아님 |
| 구현 결함·누락 테스트·검증 Finding | 해당 작업 plan/Evidence 또는 제품 Issue | 원칙적으로 아님 |
| Harness가 잘못 라우팅하거나 동일 승인 질문을 반복함 | OwnHands Feedback | 해당 |
| Harness 문제인지 제품 문제인지 아직 불명확함 | 최소한의 후보 기록과 미확인 이유 | OwnHands 행동과 관련된 가설이 있을 때만 후보 |

모든 제품 피드백을 ADR로 옮기지도 않는다. ADR은 중요한 결정의 이유, Spec은 기술 요구, Evidence는 관측을 담당한다. 필요하면 상호 링크하고 같은 내용을 여러 Source of Truth로 복제하지 않는다.

## 예시

“핵심 자료가 없으면 부분 보고서를 만들지 않고 사용자에게 자료를 요청한다”는 제품의 실패 정책이다. Spec에 요구로 남기고 중요한 대안 선택 이유가 있으면 ADR에 기록한다.

“제품 정책 선택을 OwnHands 피드백으로 잘못 분류했다”는 Harness 동작에 대한 신호이므로 OwnHands Feedback에 해당한다.

이 예시는 사용자가 제공한 회고를 공개 가능한 수준으로 정리한 것이다. 비공개 프로젝트의 전체 대화·코드·개인 자료·로컬 경로를 공개 저장소로 옮기지 않는다.

## 후속 처리와 한계

원래 사용자 교정·최초 실패 이력은 삭제해 숨기지 않는다. 기존 파일 이동이 필요하면 대상 내용을 확인한 뒤 올바른 문서와 연결하고 이력을 보존한다. 이번 문서 커밋은 사용 프로젝트의 기존 feedback 파일을 이동하지 않는다.

신호 분류의 정확성, 잘못된 자동 호출의 감소, 사용자 승인 없는 외부 Issue 생성 방지는 후속 E2E에서 확인한다. “제품 문제”라고 분류했다고 해서 실제 Harness 원인 가능성까지 배제한 것으로 기록하지 않는다.
