# ADR-0002 — Explain 스킬의 ELI5 시각 모델 수용 및 도메인 어휘 보존

- **상태:** Accepted — 사용자 합의 (2026-09-20 #138 정제: 명시적으로 HTML/아티팩트를 요청한 경우에만 적용)
- **일자:** 2026-09-18
- **관련 Issue:** [#106](https://github.com/taejung3852/OwnHands/issues/106) (선행: [#103](https://github.com/taejung3852/OwnHands/issues/103), [#104](https://github.com/taejung3852/OwnHands/issues/104))

---

## 1. Context (배경 및 문제)

1. **기존 `explain` 출력의 한계 (정보 과부하)**:
   - 초기 `explain` 스킬은 결정을 설명할 때 다크모드 엔지니어링 대시보드 형태로 수백 줄의 텍스트, 복잡한 표, SVG 사각형 안에 불릿 포인트를 나열했다 ([과거 `explain-issue-104.html`](../explain-issue-104.html) 601줄).
   - 이는 판정 기준인 *"사람이 가장 짧은 시간에 이해한다(10초 법칙)"*를 만족하지 못하고 인지 부하를 가중시켰다.

2. **`eli5` 모델의 장점과 발견**:
   - 일반 상식을 설명하는 `eli5` 스킬은 밝고 따뜻한 톤, 둥근 스토리 카드, 극소 텍스트(질문 1줄 + 설명 1줄), 친근한 블록 컴포넌트로 10초 만에 메커니즘을 납득시키는 뛰어난 시각적 UX를 지니고 있었다.

3. **기존 `eli5`를 그대로 쓰지 않고 `explain`을 재설계한 이유**:
   - **독자 대상의 차이**:
     - `eli5`의 독자는 *"해당 개념을 아예 처음 접하는 5살 아이/비전공자"*다. 따라서 용어를 지나치게 유아적이고 추상적인 비유("선수와 심판", "3총사", "친구들")로 치환한다.
     - 반면 OwnHands의 독자는 **"이 시스템을 직접 만들고 있으며, 진행 중인 결정의 인과관계와 흐름을 빠르게 복기하고 싶은 동료 엔지니어"**다. 유아용 용어는 오히려 맥락 파악을 방해한다.
   - **엔지니어링 투명성과 엄밀성 (Feynman 검증)**:
     - `eli5`는 극단적 단순화를 위해 기술적 전제와 한계를 생략한다.
     - 그러나 시스템 엔지니어링에서는 `sandbox_mode = "read-only"`의 부모 라이브 권한 override 한계, 토큰 비용 트레이드오프, 플랫폼 미확인 사양 같은 **'생략된 전제와 Gap'이 투명하게 보존**되어야 한다.
   - **영구 아티팩트 보존**:
     - `eli5`는 일회성 대화 답변 위주지만, `explain`은 Git 저장소(`docs/explain-*.html`)에 영구 보존되어 PR 리뷰어와 미래 개발자의 온보딩 기준선이 된다.

## 2. Decision (결정)

`explain`은 사용자가 스킬을 명시적으로 선택했을 때만 사용한다. 그중 HTML이나 별도 아티팩트를 요청한 경우, 산출물 구조를 **"ELI5의 시각적 스토리 카드 UX + 정확한 엔지니어링 도메인 어휘"**의 결합 모델로 적용한다.

| 구성 요소 | 설계 내용 | 채택 이유 |
|---|---|---|
| **레이아웃** | 2~3장의 독립 스토리 카드 (`1`, `2`, `3` 단계 뱃지) | 동화책을 넘기듯 순차적 호흡 제공 |
| **텍스트 밀도 제한** | **카드 1장당 굵은 제목 1줄 + 설명 1줄 (최대 2줄)** | 글 읽는 피로도를 없애고 시각 컴포넌트 배치를 강제 |
| **용어 수준** | `Subagent`, `read-only`, `구현자 편향`, `컨텍스트 오염` 등 **도메인 기술 어휘 보존** | 유아용 은유 배제, 엔지니어 간 정확한 소통 보장 |
| **시각 요소** | 역할 칩(Role Chips), 파이프라인 흐름, 대비 박스(채택 vs 기각) | 복잡한 아키텍처 결정을 10초 만에 시각화 |
| **3초 퀴즈** | `<details class="quiz-item">`으로 **정답 기본 숨김** | 능동적 자가 점검 및 클릭 토글 인터랙션 |
| **기술적 투명성** | 생략된 전제, 전문가의 예외, Gap, 링크를 **하단 `<details>`에 보존** | 본문의 단순함을 해치지 않으면서 엔지니어링 엄밀함 확보 |

## 3. Alternatives & Trade-offs (대안 및 트레이드오프 분석)

### 대안 1: 기존의 엔지니어링 대시보드(다크모드, 텍스트/표 나열) 유지
- **기각 사유**: 600줄이 넘는 텍스트를 읽어야 하므로 작업 복기 비용이 크고, 사람이 10초 안에 직관적으로 흐름을 이해할 수 없음.

### 대안 2: 외부 `eli5` 스킬을 그대로 호출하여 대체
- **기각 사유**:
  - 도메인 용어가 "3총사", "도우미" 등으로 왜곡되어 실제 TOML 설정이나 코드와의 연결고리가 끊어짐.
  - 시스템 한계와 트레이드오프가 완전히 누락되어 엔지니어링 문서로서의 신뢰성을 상실함.

### 대안 3: 네거티브 프롬프트("다크모드 금지", "표 금지")로 제어
- **기각 사유**: 네거티브 지침은 모델을 불안정하게 만들고 특정 캡처 색상에 과적합됨. "카드당 최대 2줄", "물리적 시각 메타포 컴포넌트"라는 포지티브 규격으로 유도하는 것이 훨씬 견고함.

---

## 4. Consequences (결과 및 영향)

### 긍정적 영향
- 기존 600줄 텍스트 덩어리가 2~3장의 쾌적한 시각 카드로 압축되어 누구나 10초 만에 결정 맥락을 이해 가능.
- 엔지니어링 용어가 그대로 살아 있어 실무 구현과 ADR, 이슈 간의 어휘 불일치가 발생하지 않음.
- `<details>` 블록 덕분에 단순한 시각화와 엄밀한 엔지니어링 투명성이 양립함.

### 주의 및 제약
- 카드 1장당 텍스트 2줄 상한을 어기면 다시 텍스트 덩어리로 퇴행하므로 [shape.md](../../../.agents/skills/explain/references/shape.md)의 밀도 제약을 철저히 준수해야 함.
