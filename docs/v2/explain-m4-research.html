M4에서 진짜 무엇을 만들고 버리는가?

무거운 러너 배제 • 온디맨드 Reference • Before 증거 확보

1

배보다 배꼽이 컸던 V1 검증 프레임워크는 버린다

V1의 비극 (버릴 것)
자체 러너 & 실시간 서버
• 수십 개 검증 스크립트와 파서 자체 제작
• 실시간 소켓/캐시 관리로 유지보수 폭증
• 개발보다 도구 관리에 체력 소진
V2의 원칙 (채택할 것)
Zero-Code Thin Harness
• 검증 러너는 언어 네이티브 도구 그대로 활용
• 상시 UI 대신 1회성 /explain 호출
• 가벼운 마크다운 지침과 프로토콜만 규정
2

Verifier는 테스트 재실행자가 아닌 '증거 감사관'이다

제약 분석 (보류)
Verifier 직접 재실행
• read-only 샌드박스에서 러너의 임시파일 쓰기 실패 가능성
• ⚠️ 실제 재실행 성공 여부는 미실측 상태
• 매번 두 번 실행되어 빌드 시간 2배 소요
안전한 안 (채택)
신선한 증거 역추적 감사
• Builder가 실행한 실제 터미널 출력(로그/Exit Code)을 Verifier가 read-only로 수용기준(AC)과 역추적 대조
• 거짓 완료 및 편향을 독립적으로 대조 판정
3

비교 주장을 증명하는 Before-After Baseline 후보

AI의 흔한 거짓말
Before 생략
• 재현도 안 해보고 코드만 바꾼 뒤 "고쳤습니다"
• 실제로는 버그가 안 났던 코드였거나 환각
설계 후보
bugfix/performance의 Baseline 후보
• 버그/성능 비교 주장 시 재현 로그·수치 확보
• Before 확보 불가능 시 UNOBSERVED 명시 (판정 방식은 ADR-0008에서 확정)
⚡ 3초 점검 퀴즈
Q1. M4에서 커스텀 테스트 러너나 상시 대시보드 프로그램을 만들지 않는 이유는? 정답 확인
A: V1처럼 도구 유지보수 부담이 본 개발보다 더 커지는 주객전도를 막기 위함입니다. 네이티브 테스트 도구 위에 가벼운 지침 규약(Thin Harness)만 얹습니다.
Q2. Verifier가 테스트를 직접 돌리지 않고 Builder의 실행 증거를 감사하는 이유는? 정답 확인
A: read-only 샌드박스의 파일 쓰기 충돌 가능성을 피하고 Evidence 대조에 집중하기 위함입니다. Builder가 남긴 실제 터미널 출력(Fresh Evidence)을 기획서의 AC와 독립적으로 역추적 대조합니다.
