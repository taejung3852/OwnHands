기본 규칙 ↔ 회사 규칙 (#105), GORE로 역할 나누기

구현 세부사항으로 직행하지 않고, 최상위 목표에 사람과 에이전트의 역할을 닻(Anchor) 내립니다.

1
GORE: 최상위 목표에 먼저 닻(Anchor)을 내린다
코드나 알고리즘부터 짜는 '상향식(Bottom-Up)' 함정을 피하고, 사람이 원하는 실제 가치에서 시작합니다.
⚓
최상위 목표: "기본 개발 흐름을 다시 구현하지 않고, 회사/팀 규칙을 자연스럽게 덧붙여 실무 무기로 쓴다"
인간의 실무 의도 ➔ 플랫폼 네이티브 팩트 ➔ 최소 연결 설계 (Zero-Code)
2
역할 분담: 의도와 경계(인간) vs 팩트와 구조(에이전트)
각자가 가장 잘할 수 있는 영역에 집중하여 시스템 비대화와 환각을 원천 차단합니다.
👤 사람 (User)
의도 · 경계 · 판정
• 실제 원하는 사용 모습 제시
  ("기본 템플릿에 팀 규칙을 어떻게 얹을까?")
• 비목표(Non-goals) 승인
  ("복잡한 Policy Resolver 코드는 안 만든다!")
• 결정 상태 승격
  (생각 🤔 ➔ 확정 ✅ 최종 판정)
🤖 에이전트 (Antigravity)
팩트 · 메커니즘 · 문서화
• Codex 공식 네이티브 팩트 조사
  (개인 기본값, 모듈 override, 거버넌스 분리)
• 경량 연결 지점 초안 작성
  (코드를 안 짜고도 연결되는 구조 설계)
• ADR-0005 작성 및 상태표 정합
  (미결정 사항을 확정으로 위장하지 않음)
3
우리가 절대 빠지지 말아야 할 함정 (Anti-patterns)
OwnHands의 AGENTS.md 규율에 따라 공식과 우리 결정을 엄격히 분리합니다.
❌ 피할 함정
과설계 & 위장: 아직 오지도 않은 가상 회사 정책을 위해 복잡한 우선순위 알고리즘을 코드로 짜거나, 사용자의 "아이디어(🤔)"를 확정된 규칙인 양 멋대로 코딩하는 것.
✅ GORE 방식
네이티브 활용 & 정직함: Codex의 디렉터리 계층 기능을 활용해 최소한의 연결 방향만 확정하고, 코드는 한 줄도 짜지 않으며, 합의 전까지 🤔 상태를 정직하게 유지하는 것.
스스로 확인하는 점검 퀴즈
질문을 읽고 정답 확인 버튼을 눌러보세요!
Q1. GORE(목표 지향 요구공학)에서 구현 세부사항보다 항상 먼저 와야 하는 것은? 정답 확인
💡 최상위 목표와 사용자의 의도(Top-Down Intent)입니다! 구현에 매몰되기 전에 "우리가 이걸 왜 만드는가"에 먼저 닻을 내립니다.
Q2. 이슈 #105에서 '우선순위 알고리즘'이나 'Policy Resolver'를 코드로 짜지 않는 이유는? 정답 확인
💡 과설계(Non-goal)이기 때문입니다! Codex가 이미 지원하는 계층 override 기능을 활용하면 복잡한 코드 없이도 경량 연결 지점을 설계할 수 있습니다.
