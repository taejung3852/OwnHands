# 개발 방법 — 각 마일스톤을 어떻게 진행하는가

> 이 문서는 **작업 방식의 원칙**이다. V1에서 얻은 교훈이 그대로 반영돼 있다.

---

## 왜 이 방법인가

V1에서 유지보수 부담이 커진 원인은 검증 원칙이 아니라, **그 원칙을 떠받치려고 직접 만들어 운영해야 했던 시스템의 크기**였다.

> "주객전도가 되는 상황 즉, 배보다 배꼽이 더 커지는 현상이 생긴거 같아."

그리고 실제로 확인해 보니, **플랫폼이 이미 제공하는 것이 있었다.**
Codex는 Skills·Hooks·Subagents·MCP·샌드박스·지침 계층을 네이티브로 제공한다(확인일 2026-09-16). → [Codex 공식 문서](../references/codex-official.md)

그래서 V2의 첫 질문은 "어떻게 만들까"가 아니라 **"만들어야 하나"**다.

---

## 마일스톤 진행 순서

```text
Research → Native 기능 대응 → 수단 선택 → 만들지 않을 것 결정
→ 최소 구현 → 실제 작업/Eval로 확인
```

### 1. Research — 공식 자료를 먼저 읽는다

> "항상 중심은 공식문서와 아까 너한테 줬던 anthropic 블로그가 될 거야."

조사는 **"지원하는가"에서 멈추지 않는다.** 그것만 보면 형식은 맞고 내용은 감으로 쓰는 결과가 된다.

| 확인할 것 | 예 |
|---|---|
| 형식과 지원 범위 | 파일 위치, 필수 필드, 상한, 어느 표면에서 동작하는가 |
| **작성 방식** | `description`을 어떻게 써야 의도대로 호출되는가, 지침에 무엇을 넣고 무엇을 Reference로 빼는가, (사용한다면) MCP 도구 설명을 어떻게 쓰는가 |

공식 자료에 작성 가이드가 있으면 그것을 따르고, 없으면 **없다고 기록한 뒤 실제 Eval로 확인한다.**

**읽지 못한 자료를 읽었다고 기록하지 않는다.** 커뮤니티 글로 조용히 대체하지 않는다. 기억에 의존해 설정 키나 지원 기능을 만들어내지 않는다.

문서가 이동·개편됐다면 공식 연결을 확인한다.
> 실제 사례: `developers.openai.com/codex/*`는 2026-09-16 확인 시점에 `learn.chatgpt.com/docs/*`로 308 이동해 있었다.

**원문은 Markdown twin으로 받는다.** Codex 문서는 페이지 URL에 `.md`를 붙이면 원문을 그대로 준다. 전체 인덱스는 `learn.chatgpt.com/llms.txt`, 전량 단일 파일은 `learn.chatgpt.com/docs/llms-full.txt`다.

**근거를 찾지 못했을 때의 기록 방식.** 관련 페이지를 확인하고 공식 corpus 전량을 검색한 뒤에도 근거를 찾지 못하면, **"현재 공식 문서에서 확인하지 못함"으로 기록한다.** 페이지 하나를 읽고 없다고 단정하지 않는다.

> ⚠️ **검색 실패를 기능 부재의 증명으로 취급하지 않는다.** "전량 검색했는데 없다"는 `미확인`의 근거이지 `지원하지 않음`의 근거가 아니다.

→ 적용 예: [Codex 공식 문서 확인 §0.2](../references/codex-official.md)

### 2. Native 기능 대응 — 플랫폼이 이미 하는 것을 찾는다

> 이 마일스톤에서 Codex가 이미 제공하는 것은 무엇인가?

### 3. 수단 선택 — 무엇을 어디에 둘지 정한다

| 구성 | 책임 |
|---|---|
| 프로젝트 지침 | 공통 맥락과 기본 작업 원칙 |
| Skill | 언제 무엇을 하고 어떤 결과를 내는지 |
| Reference | 특정 상황의 자세한 지식 |
| Agent/Subagent | 독립된 역할·맥락·도구로 수행 |
| Tool·Script | 실제 동작 |
| Hook·권한·CI | 실행 경계·자동 검사 |

**V1에서 이 구분 없이 진행한 것이 부담의 큰 원인이었다.**

### 4. 만들지 않을 것 결정 — 명시적으로 기록한다

> **무엇을 직접 만들지 않아도 되는가?**

이 질문의 답을 기록으로 남긴다. 나중에 같은 것을 다시 만들지 않기 위해서다.

### 5. 최소 구현

필요한 만큼만 만든다. 미래를 가정한 범용 추상화를 미리 만들지 않는다.

> ⏳ **두 번째 플랫폼의 실제 필요를 확인하기 전에 범용 adapter나 공통 실행 엔진을 확정하지 않는다.**

### 6. 실제 작업/Eval로 확인

만든 것을 실제 작업에 써 보고, 작은 Eval로 나아졌는지 확인한다.
✅ 이것은 **V2-M1부터** 한다. M5까지 미루지 않는다.

## 조사 결과를 남기는 최소 형식

```text
공식 URL과 문서/절
확인일과 적용 환경
확인한 동작과 제약
OwnHands에 주는 의미
직접 만들지 않아도 되는 것
아직 확인하지 못한 것
```

**마지막 줄이 중요하다.** 확인하지 못한 것을 `없음`이나 `해당 없음`으로 추정하지 않는다.
→ 적용 예시: [Codex 공식 문서 확인 기록](../references/codex-official.md)

## 근거는 역할별로 사용한다

| 판단 | 근거 |
|---|---|
| 어떤 제품을 왜 만들 것인가 | **사용자 의도**와 확정된 제품 방향 |
| AI-native SDLC의 큰 틀 | **Anthropic Playbook**과 그것에 대한 자체 적용 판단 |
| Codex의 실제 형식·기능·권한·제약 | **Codex 최신 공식 문서** |
| 모델별 prompting·위임 특성 | 해당 모델의 공식 가이드와 실제 평가 |
| 조직의 실제 의무 | 권한 있는 조직 정책 원문과 책임자 |
| 실행이 실제로 성공했는가 | 대상 버전과 환경이 기록된 **실행 근거** |

**세 가지 혼동 금지**

1. 공식 문서를 근거로 **사용자의 제품 의도를 덮어쓰지 않는다.**
2. **Anthropic의 예시를 Codex의 지원 기능으로 취급하지 않는다.**
3. Codex App/CLI/IDE와 일반 API·SDK의 **적용 범위를 구분한다.**

Anthropic 원문 전체를 저장소에 복제하지 않는다. 짧은 요약·출처·사용자에게 준 의미·자체 선택을 구분한다.
**글의 예시 숫자나 조직 구조를 OwnHands의 의무로 추가하지 않는다.**

## 과설계를 막는 제한

이 프로젝트에서 새로 만들지 않기로 한 것들이다.

| 만들지 않을 것 | 이유 |
|---|---|
| 전용 문서·Project·Wiki 동기화 서비스 | 같은 원문을 링크하면 된다 |
| 새 Dashboard·상시 업데이트 사이트 | V2 전환 방향과 반대다 |
| 범용 Policy Resolver·Universal Adapter | 아직 설계하지 않았고 실제 플랫폼별 요구가 먼저다 |
| 모든 문서·문장을 검사하는 Validator | 편집과 링크 확인을 새 제품 개발로 만들지 않는다 |
| 미래의 모든 기능을 상세 구현 이슈로 발행 | 로드맵 이후 착수 시 공식 조사와 함께 결정한다 |

> **코드량·문서량·테스트 수가 많다는 이유로 작업을 잘했다고 판단하지 않는다.**
> 필요한 설명의 깊이는 확보하되 같은 내용을 여러 곳에 반복하지 않는다.

## 검증에서 지킬 것

V1의 실제 경험에서 얻은 원칙이다.

| 원칙 | 뜻 |
|---|---|
| **계약은 강하게 검증** | 보안, 상태 의미, read-only, 근거 무결성, stale/unknown 구분 |
| **구현 형태는 느슨하게 검증** | 함수 호출 횟수·특정 함수명·코드 배치·문자열 개수를 고정하지 않는다 |
| **현재 필요한 만큼만 수정** | 미래를 가정한 범용 스캐너·추상화·프레임워크를 만들지 않는다 |
| **중복은 같은 작업 안에서 정리** | 단, 재사용 가능성을 상상해 미리 큰 추상화를 만들지 않는다 |

테스트를 쓰기 전에 **"이게 계약인가 구현 모양인가"**를 먼저 판별한다.

> **테스트 통과 수를 제품 유용성이나 사용성의 증거로 바꾸지 않는다.**
> 확인하지 못한 것은 "관찰 못 함"으로 정직하게 남긴다.
