1차 자료 발견 ① : intent.md vs spec.md 해부도
왜 두 문서를 분리하며, 각 문서 안에는 무엇이 들어가야 하는가?
📄 intent.md 사람이 작성/승인
질문: "왜, 무엇을 하려는가?"
  • 📌 문제 정의 및 비즈니스 배경
  • 🎯 목표 결과 및 사용자 가치
  • 🚫 비목표 (안 할 것 / Non-goals)
  • ⚠️ 핵심 제약 (Constraints)
📄 spec.md AI 분석 ➔ 사람 승인
질문: "어떤 기술 구조로 만족시킬 것인가?"
  • ⚙️ 기술 요구사항 (Requirements)
  • 🏛️ 시스템 아키텍처 및 인터페이스
  • 🔍 엣지 케이스 (Edge cases)
  • 🎯 수용성 기준 (Acceptance Criteria)
🛡️ 분리하는 가장 큰 이유 (Human Gate): 사람이 문제 정의(Intent)에 도장 찍기 전에 에이전트가 복잡한 기술 설계(Spec)로 직행하여 토큰과 시간을 낭비하는 것을 막기 위함!

1차 자료 발견 ② : 플랫폼(Codex)의 팩트와 공백(Gap)
플랫폼이 실제로 지원하는 것과 지원하지 않는 것을 명확히 구분했습니다.
✅ 확인된 사실 (Fact)
디렉터리 깊이 기반 Override & 32 KiB 천장
~/.codex/ ➔ Git Root ➔ 하위 폴더 순으로 읽으며 가까운 파일이 상위를 덮어씁니다. 합산 크기가 32 KiB를 넘으면 하위 지침이 프롬프트에서 잘립니다.
⚠️ 확인된 공백 (Gap — 문서에 없는 것)
Codex에는 intent/spec 기능 및 우선순위 알고리즘이 없음
OpenAI Codex에는 intent.md를 자동으로 다루는 기능도, "Company 규칙이 기본 규칙을 우선한다"는 강제 알고리즘도 없습니다. 순전히 우리가 정해야 하는 워크플로 규약입니다.
3
조사 결론 : OwnHands의 M2 산출물 규격 확정
32 KiB 상한을 지키면서 10초 만에 스캔할 수 있는 가벼운 3칸 규격입니다.
intent.md 3칸 규격
1. ## 문제 및 배경 (Why) 2. ## 목표 결과 및 가치 (What) 3. ## 비목표 및 제약 (Boundaries)
spec.md 3칸 규격
1. ## 기술 요구사항 (Reqs) 2. ## 시스템 구조 (Architecture) 3. ## 수용성 기준 (Acceptance)
📁 저장 위치: docs/v2/specs/<feature-name>/ (세션 휘발 방지 및 Git 영구 보존)
💡 스스로 풀어보는 3초 퀴즈
Q1. intent.md와 spec.md의 가장 결정적인 내용 차이는? 정답 확인
👉 intent.md는 '문제와 가치(Why/What)'를 사람이 정의하는 원형 명세이고, spec.md는 '기술 구조와 수용 조건(How/Architecture)'을 AI가 코드베이스와 대조해 작성하는 기술 청사진입니다.
Q2. Codex의 32 KiB 한도가 우리에게 주는 설계 제약은? 정답 확인
👉 AGENTS.md에 방대한 지식이나 템플릿을 다 때려 넣으면 뒤쪽이 잘립니다. 따라서 정책은 핵심 원칙만 얇게 두고, 세부 사양은 Reference나 specs 문서로 분산해야 합니다.
