## 1. 초기 작은 Eval (V2-M1 ~ V2-M4)

### 1.1 어떻게 시작하는가
- **대표 과제 선정 원칙**:
  1. 인위적으로 꾸며낸 가상 과제가 아니라, **실제 일상 협업과 산출물에서 나온 과제**를 선정한다.
  2. 에이전트 시스템 자산(지침, 스킬, 서브에이전트 정의)이 변경될 때 즉시 영향을 받는 지점을 고른다.
  3. ⚠️ **테스트 중 외부 부작용 방지**: 테스트 실행 도중 실제 GitHub 이슈나 PR을 생성하지 않으며, 초안(Draft) 또는 샌드박스 내 실행으로 제한한다.
- **결과 기록 방식**:
  - `docs/v2/evals/` 디렉토리 아래 순번형 마크다운(`0001-...md`)으로 보존한다.
  - 잘 나온 결과만 골라내지 않고, 관측된 실패·오발·한계를 가감 없이 원본 그대로 기록한다.
  - 동일한 캐시 조회를 독립 생성 평가로 부풀려 계산하지 않는다.

### 1.2 현재 축적된 초기 작은 Eval 목록
1. [Eval 0001: Skill 라우팅 정확도 평가](0001-skill-routing.md)
   - 5대 일상 프롬프트에 대한 라우팅 일치율 및 초안 작성 제약 준수 평가.
2. [Eval 0002: Verifier 독립 검증 평가](0002-subagent-verifier.md)
   - 구현자 편향 없는 독립 수용성 기준 대조 및 Read-only 불변성 평가.
3. [Eval 0003: Researcher 1차 자료 조사 및 지침 유효성 평가](0003-subagent-researcher.md)
   - 1차 출처 URL 직접 인용, 사실/공백 엄격 분리, 코드 무단 수정 방지 지침 평가.
4. [Eval 0004: grill-spec 도우미 Skill 동작 및 추적성 평가](0004-skill-grill-spec.md)
   - 팩트/결정 분리, 8단계 프로토콜, 3대 안전장치, M2 파이프라인 관통 실측 적합성 평가.

## 2. V2-M5 확장 기준 (체계로의 도약)

V2-M5에서는 M1~M4 동안 축적된 개별 마크다운 평가 사례를 체계로 확장한다.  
⚠️ **정확한 구현은 M5에서 설계하며, 아래는 현재 고려 중인 확장 구현 후보(예시)다.** 확정된 설계나 고정 규칙이 아니다.

| 구분 | 초기 작은 Eval (M1~M4) | M5 확장 구현 후보 (예시) |
|:---|:---|:---|
| **실행 주체** | 대화 세션 내 페어 프로그래밍 실측 | 비대화형 자동 러너 후보 (CLI / CI 등) |
| **과제 데이터셋** | 문서 내 기록된 대표 시나리오 | 버전 관리되는 Task Set 후보 (JSON/YAML 등) |
| **판정 방식** | 정성적 관측 + 수작업 결과 대조 | 사전 정의된 기준선(Baseline) 대비 자동 채점 후보 |
| **회귀 판단** | 변경 후 즉시 수동 확인 | Git Hook 또는 CI 게이트웨이 연계 검토 후보 |
| **부작용 제어** | "초안만 작성" 프롬프트 제약 | Mocking / Dry-run 강제 샌드박스 인프라 후보 |

## 3. 주의 사항 및 지침

1. **테스트 통과 수의 착시 경계**:
   - 단위 테스트나 Eval 통과 건수 자체를 제품의 완성도나 유용성의 완전한 증거로 환치하지 않는다.
2. **공식 vs 자체 결정 구분 (AGENTS.md 준수)**:
   - Anthropic Playbook이나 Codex 공식 문서가 제시한 예시 지표(통과율 임계치 등)를 우리 시스템의 고정 규칙으로 둔갑시키지 않는다.
