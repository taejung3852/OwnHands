검증 지식은 어디에 두고, Verifier는 무엇을 감사하는가?

온디맨드 Reference • Fresh Evidence 독립 감사관 • Before 기준선 프로토콜

1

검증 지식의 자리: 상주 대신 핀포인트 온디맨드 로드

카탈로그 10,000 토큰 천장을 지키기 위해 검증 문서는 docs/v2/references/에 보관하고 실행 시에만 읽습니다.

금지 (컨텍스트 낭비)
상시 프롬프트 주입
• AGENTS.md나 Skill 본문에 모든 검증 가이드를 통째로 삽입
• 초기 토큰 예산 고갈 및 핵심 지침 집중도 저하
채택 (Progressive Disclosure)
plan.md 핀포인트 링크
• docs/v2/references/*.md에 영구 보존
• plan.md 태스크 매핑 시 해당 가이드만 핀포인트로 view
2

Verifier의 역할: 직접 달리는 러너가 아닌 '독립 감사관'

read-only 제약과 중복 실행 비용을 피해 Builder의 실제 터미널 출력(Fresh Evidence)을 AC와 역추적 대조합니다.

Builder (구현)
네이티브 러너 실행
➔
Fresh Evidence
Exit 0 / 커밋 / 로그
➔
Verifier Subagent
read-only 독립 대조
➔
판정 (3종)
PASS / FAIL / UNOBSERVED
3

Before 기준선: '고쳤다'는 주장은 '고치기 전 실패'로 입증한다

버그 수정과 성능 개선은 작업 전 결함/수치를 남겨야 하며, Before 증거가 없으면 PASS 대신 UNOBSERVED 처리합니다.

AI의 자가합리화
Before 없는 개선 주장
• 결함 재현 없이 코드 고친 뒤 "버그 잡았습니다"
• 기준 수치 없이 "성능이 2배 빨라졌습니다"
• ➔ 입증 불능 및 허위 개선 리스크
ADR-0008 프로토콜
Claim별 엄격 대조
• bugfix: Before 실패 로그 ➔ After 미재현 대조
• performance: Before 수치 ➔ After 동일 벤치 대조
• Before 부재 시: [UNOBSERVED] 플래그 부여
⚡ 3초 점검 퀴즈
Q1. Verifier가 직접 테스트를 재실행하지 않고 Fresh Evidence를 역추적 감사하는 이유는? 정답 확인
A: read-only 샌드박스의 파일 쓰기 충돌을 원천 방지하고, 중복 실행 비용 없이 가벼운 감사(Thin Harness)를 완성하기 위함입니다. Builder가 plan.md에 남긴 실제 터미널 출력(명령어, exit code, assertion 결과)을 기획서의 수용 기준(AC)과 독립적으로 교차 대조합니다.
Q2. 버그 수정 작업에서 Before 결함 재현 로그 없이 코드만 고쳐서 제출하면 Verifier의 판정은? 정답 확인
A: 무조건 FAIL이 아니라 [UNOBSERVED](미관측)로 판정합니다. 사전에 결함이 명확히 입증되지 않은 채 코드만 변경되었음을 정직하게 기록하여, AI의 거짓 개선 주장이나 자가합리화를 방지합니다.
